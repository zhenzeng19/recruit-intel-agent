## 零、先做数据体检（用你真实采集的数据，不猜）

我把你库里 4 条真实采集的简历全看了一遍，结论是：

### 0.1 你给的详情页 URL 确实带真 ID，但我们没在用

| 候选人 | 平台内 ID（现在存的） | `resumeUrl`（现在存的） |
|---|---|---|
| 孙先生 | `content:y0c5r7` ❌ 内容指纹 | `https://lpt.liepin.com/recommend#preview` ❌ **列表页** |
| 李先生 | `content:15hq7ar` ❌ 内容指纹 | `https://lpt.liepin.com/recommend#preview` ❌ **列表页** |
| **周敏** | `content:8gwfzr` ❌ 内容指纹 | ✅ 详情页 URL（就是你发我的那条） |

**两个结论**：
1. **`resumeUrl` 存成列表页是必然的** —— 因为我们存的是「采集那一刻的 `location.href`」。从 `/recommend#preview` 预览面板采的，`location.href` 就是列表页。而详情页那条（周敏）存对了，恰恰因为那次是在详情页采的。
2. **你给的详情页 URL 里明明有 `resIdEncode=CD34EF56AB7800cc33dd44`，周敏的平台 ID 却还是内容指纹** —— 因为 `resIdEncode` **不在我们的 ID 参数表里**。加了它，详情页采集就能拿到真 ID。

> ⚠️ **内容指纹当 ID 的真实代价**：同一人从预览面板采一次、从详情页采一次，容器边界不同 → 指纹不同 → **存成两条档案**。你库里现在就是「预览面板 3 条 + 详情页 1 条」这种混合状态，未来会越来越乱。这一条必须修。

### 0.3 一个必须先讲清的期望边界

- **附件简历抓不到**：正文写着「已上传附件简历 / 向TA索要后才可查看」。也就是说候选人真实的 PDF/Word 简历**需要我们主动索要**，我们导出的是**在线简历文本**排出来的 PDF。这点必须在 PDF 上注明，否则业务部门会以为是原件。
- **来源链接给业务部门点不开**：详情页 URL 带 `sign`/`sss` 签名参数，而且需要**登录你这个 HR 账号**才有权限。所以链接只对你自己的溯源有用，**PDF 才是给业务部门的东西**。

## 一、Phase A：先修数据（否则 PDF 和来源都是错的）

这一步必须在导出之前做，否则导出的 PDF 没有岗位、来源也是列表页。

### A1. 补上 ID 参数（一行改动，立刻见效）

```ts
// apps/extension/src/extract.ts — SITE_LIEPIN.idParams 最前面插入
idParams: [
  'resIdEncode',    // ← 详情页的真简历 ID（你给的 URL 里那个）
  'usercIdEncode',  // ← 候选人 ID
  'ejobId',         // ← 职位 ID（不是候选人，但可留作上下文）
  'resumeId', 'resumeid', 'resume_id', ...（原有）
]
```

⚠️ 顺序有讲究：`resIdEncode` 必须排在前面 —— `pickCandidateId` 是「取第一个命中的」。`ejobId` 要排在候选人 ID 之后（它是职位不是人）。

### A2. 从 DOM 里找「这份简历自己的链接」（**关键改动**）

只补 A1 解决不了「预览面板采到的还是列表页」这个问题。做法：

在预览面板采集时，**在简历容器附近找详情页链接**：
```
在容器内 + 容器祖先（向上 3 层）里查 a[href*="resIdEncode"] / a[href*="/resume/detail?"]
  → 找到就把 href 里的 resIdEncode 当作平台 ID，并把 href 当作 resumeUrl
```
这**一石二鸟**：
- 来源 URL 变成「这份简历自己的链接」，不管从哪个入口采的；
- 预览面板与详情页两条路**收敛到同一个平台 ID** → 不再重复建档。

猎聘预览面板上有「全屏 / 新页面查看」这类按钮，其 `href` 应该就是详情页 URL —— 但**我不能凭猜写选择器**。所以策略是：
- 先上线一个**宽松版**：扫 DOM 里所有 `a[href]`，只要 href 匹配 `/resume/detail?` 或含 `resIdEncode=` 就采用（不依赖具体 class）；
- 同时把「找到没找到、href 长什么样」打进 `__ria.scan()` 的诊断输出，你下次跑一次我就能确认并收紧。

### A3. 剥掉尾部 UI 噪声（**同时修掉一个判重 bug**）

把 `觉得TA还不错` 之后的整段 UI chrome 处理掉：
- 方案：新增 `stripResumeChrome(text)`，**在容器文本进入指纹计算前**就切掉尾部（从 `觉得TA还不错` / `获取电话`+`剩N次权益` / `人才招聘记录` 这类标志行开始）。
- 为什么必须在**指纹之前**：`剩10次权益`、`本月剩余30次` 会变，留在指纹里就等于「同一份简历每天一个新指纹」。

补充把这些词加进 `UI_CHROME_WORDS`：`剩N次权益`（正则）、`本月剩余N次`、`免费权益`、`超级聊聊`、`操作记录`、`人才招聘记录`、`简历备注`、`获取电话`、`向TA索要`、`已上传附件简历`、`已上传个人作品`。

### A4. 顺手记下「简历编号」

正文里的 `简历编号: EF56AB78CD9000ee55ff66` 可以作为一个新字段 `resumeNo`：
- 展示用（HR 报问题时有唯一编号，比内容指纹好沟通）；
- 将来可当**辅助去重键**（比内容指纹硬）。

### A5. 存量数据修复

`scripts/repair-data.mjs` 已经能做「重跑字段提取 + 合并重复」。这次要给它加两步：
1. **重算 resumeUrl**：从已存的 `rawText` 里**看不出**详情页链接（那是 DOM 里的），所以**老数据的来源 URL 修不了** —— 只能修 ID 与正文清洗。这点要如实说明：**来源 URL 只能从今往后正确**。
2. 剥掉正文尾部噪声后**重算一次判重**：如果两条档案清洗后指纹相同 → 合并。

> 👉 现实结论：`周敏` 那条的来源是对的，其余 3 条的来源 URL **无法回溯修正**（DOM 信息没保存）。要拿到正确来源，需要你重新打开那几份简历各采一次。**这是「采集时该存什么」的教训：DOM 里的一次性信息，当时不存就永远没了。**

## 二、Phase B：把正文解析成结构化简历

`packages/shared/src/resume-text.ts` 新增 `parseResumeSections(text)`：

```ts
export interface ResumeSections {
  intention?: { positions: string[]; salary?: string; cities: string[]; industries?: string[] }
  experiences: Array<{ company: string; title?: string; period?: string; duration?: string; bullets: string[] }>
  education: Array<{ school: string; degree?: string; major?: string; period?: string; tier?: string; mode?: string }>
  projects: Array<{ name: string; period?: string; title?: string; company?: string; bullets: string[] }>
  skills: string[]
  languages: string[]
  resumeNo?: string
  /** 结构化失败时的降级：按章节切出的原始段落 */
  fallbackBlocks: Array<{ title: string; lines: string[] }>
}
```

**解析策略（分层降级，永不「解析失败就空白」）**

| 层 | 依据 | 置信度 |
|---|---|---|
| ① | `*该段内容已整合附件简历信息` 块结束标记 → 切块；块内按「公司行 / 职位行 / 时间行 / 其余为描述」归类 | 高（猎聘专用但很稳） |
| ② | 章节词定位（`工作经历` / `教育经历` / `项目经历` / `技能标签` / `求职意向` / `语言能力`）→ 在章节内做 ① | 中 |
| ③ | 只有章节词、块内没有结束标记（比如 `/recommend` 预览面板的短文本）→ 段落原样保留，只分节不细分 | 中低 |
| ④ | 什么都不认 → `fallbackBlocks` 按原行输出 | 保底 |

**关键点：把置信度一起返回**（`sections.confidence: 'high' | 'medium' | 'low'`）。低置信度时 PDF 会**按原文原样排版**并在页脚标注「本页内容由页面文本自动分节，可能不完全准确」——**宁可朴素也不能印错**。

**验收**：用你库里 4 条真实简历跑一遍，人工核对分节结果；`test-store.mjs` 加断言锁定块切分与降级行为。

## 三、Phase C：打印页（PDF）

### C1. 为什么用「浏览器打印」而不是服务端生成 PDF

| 方案 | 中文 | 依赖 | 本机可行性 | 结论 |
|---|---|---|---|---|
| **浏览器打印成 PDF**（服务端渲染一个打印优化 HTML → `window.print()`） | ✅ 用系统字体，不会乱码 | **零新增依赖** | ✅ | ✅ **推荐** |
| 服务端 PDF 库（pdfkit / @react-pdf） | ⚠️ 必须**嵌入中文 TTF**（10–20MB）并手写排版 | 大 | 可行但工作量大 | 备选 |
| 无头 Chrome / puppeteer 截图或打印 | ✅ | Chromium ~150MB | ❌ **本机已确认两次不可用**（无头 Chrome 拿不到输出，文档里都有记录） | ❌ 排除 |

> 选浏览器打印还有个额外好处：**便携包里也能用**（不需要往包里塞字体文件和 PDF 引擎）。

### C2. 打印页设计

```
GET /print/:candidateId?positionId=&score=1&source=1&raw=0&auto=1
```

- **服务端渲染一份自包含 HTML**（内联 CSS、无外部资源、无框架）—— 这样它也能被单独「另存为 HTML」发出去，且不依赖看板的 JS 启动。
- A4 版式，参考猎聘的分节：头部（姓名 + 基本信息 + 求职意向）→ 工作经历 → 项目经历 → 教育经历 → 技能标签 → 语言能力。
- **页眉/顶部信息条**：
  ```
  ┌────────────────────────────────────────────────┐
  │  李先生                          应聘岗位        │
  │  38 岁 · 盐城 · 本科(非统招)      项目经理（基建） │
  │  某某师范大学 · 计算机科学与技术    匹配度 84 分   │
  └────────────────────────────────────────────────┘
  ```
- **页脚**（每页都有）：
  ```
  来源：lpt.liepin.com/resume/detail?resIdEncode=CD34EF56AB78… ｜ 采集时间 2026-10-05 03:10 ｜ 采集方式：手动保存
  本简历由「招聘捕手」从猎聘在线简历文本自动生成，非候选人原附件简历，仅供内部招聘评估使用。
  ```
- `@media print` 隐藏一切非正文元素；`?auto=1`（默认）时页面加载后自动唤起打印对话框；`auto=0` 用于纯浏览。
- **降级**：`confidence` 低时按原文原样排版（第三节的 ④）。
- **批量**：`GET /print/batch?ids=a,b,c&positionId=` → 一页多人，每人 `page-break-before: always`。

### C3. 字体

用系统字体栈，**不嵌入任何字体文件**：
```css
font-family: "Microsoft YaHei", "PingFang SC", "Hiragino Sans GB", "Source Han Sans SC", system-ui, sans-serif;
```
这是「中文不会乱码」的关键 —— 浏览器打印时用本机字体，无需我们提供字体文件。

## 六、需要你拍板的 6 个点

| # | 问题 | 我的建议 |
|---|---|---|
| 1 | **PDF 生成方式** | **浏览器打印**。「导出 PDF」= 打开打印页并自动唤起打印对话框，你在对话框里选「另存为 PDF」。**代价：多一次点击 + 一次选择**；换来零依赖、中文不乱码、便携包也能用。不接受的话只能上服务端 PDF 库（要嵌中文字体，工作量大得多） |
| 2 | **来源 URL 只修未来，修不了存量** | 接受。其余 3 条要拿到正确来源，需要你重新打开各采一次（DOM 里的一次性信息当时没存就没了）。要我把这句写进文档吗？ |
| 3 | **要不要「按岗位批量导出成一个 PDF」** | **建议要** —— 这就是「分岗位给业务部门」的正解，比逐份导出实用得多 |
| 4 | **PDF 上印不印匹配度与命中点** | 默认**印**（你转给业务部门时通常希望带上你的判断），但给开关可关 |
| 5 | **要不要印来源链接** | 建议**印在页脚**，但明确标注「需登录猎聘招聘账号查看」——免得业务部门点不开以为链接坏了 |
| 6 | **低置信度时的行为** | **降级为按原文章节排版 + 页脚注明**，绝不因为解析不确定就不给导出 |

另外一个要提醒的点：**「姓名 + 岗位」这两个信息里，岗位来自 `matches`**。你库里现在 3 条真实简历都被规则挂到了 `C++ 软件工程师`（40–55 分，因为它们是项目经理/工艺方向，而你的岗位里原先没有匹配的）。所以导出前**先去「岗位管理」把岗位建好、或在导出时手动选岗位**（打印页支持 `?positionId=`）。否则 PDF 上印的岗位会是错的 —— 这正是「保存时选岗位」那套机制要发挥作用的地方。
