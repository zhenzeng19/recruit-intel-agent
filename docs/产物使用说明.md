# 编译产物的使用方法

`npm run build` 之后，所有可交付的东西都在这里：

```
E:/zzl_workbuddy_datas/招聘agent-build/
├── server/index.js      ← 后端（1.8MB 单文件，已含全部依赖，自包含）
├── web/                 ← 前端看板（纯静态：index.html + assets/）
└── extension/           ← 浏览器扩展（manifest.json + background.js + content.js）
```

对应三种用法：**后端 + 前端一起跑**（方式一，最常用）、**前后端分体部署**（方式二）、**扩展装进浏览器**（方式三）。

---

## 方式一（推荐）：一条命令跑起整个应用

后端会**顺便托管前端静态产物**，所以前后端同源、没有跨域问题，一个端口搞定。

```bash
cd E:/zzl_workbuddy_datas/招聘agent
npm run start
```

然后浏览器打开：

```
http://localhost:8787/
```

终端会打印：

```
已托管前端静态产物：E:\zzl_workbuddy_datas\招聘agent-build\web
招聘情报 Agent 已启动：http://localhost:8787
看板入口：http://localhost:8787/
```

### 关于这台机器

- **目标机器只需装 Node 20+，不需要 `npm install`** —— `server/index.js` 是把 fastify 等依赖全部打进去的自包含单文件
- 想确认产物是否完整，直接跑：

```bash
node E:/zzl_workbuddy_datas/招聘agent-build/server/index.js
```

（效果和 `npm run start` 一样，后者只是帮你把路径拼好并带了信号转发）

### 改端口

```bash
# 临时改
SERVER_PORT=9000 npm run start

# 永久改：编辑仓库根的 .env
SERVER_PORT=9000
```

> 改了端口记得同步改 `.env` 里的 `VITE_API_BASE` 并重新 `npm run build`，
> 否则浏览器扩展还会往旧端口上报。

### 让它常驻后台

`npm run start` 是前台进程，关掉终端就停了。要常驻可以用 pm2（需自行 `npm i -g pm2`）：

```bash
pm2 start "E:/zzl_workbuddy_datas/招聘agent-build/server/index.js" --name 招聘情报
pm2 save
```

## 方式二：前后端分体部署

前端交给 nginx / 静态托管，后端单独跑。**关键点：`/api` 必须反向代理到后端**，
因为前端请求用的是相对路径 `/api/...`，必须同源。

### 1）先起后端

```bash
node E:/zzl_workbuddy_datas/招聘agent-build/server/index.js
# 监听 0.0.0.0:8787
```

### 2）再把 `web/` 交给 nginx

把 `招聘agent-build/web/` 整个目录拷到服务器，比如 `/var/www/ria/web`，然后：

```nginx
server {
    listen 80;
    server_name your-domain.com;

    root /var/www/ria/web;
    index index.html;

    # 接口反代到后端
    location /api/ {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # SPA 回退：前端路由交给 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### 不配反代会怎样

前端会去请求 `your-domain.com/api/...` 而 404。后端虽然开了 CORS（`origin: true`），
但前端用的是相对路径，跨域配置帮不上忙——**所以必须反代，或者让后端直接托管前端（方式一）**。

## 方式三：浏览器扩展怎么装

> 📖 **完整图文步骤见 [Edge安装扩展指南.md](./Edge安装扩展指南.md)**（含验证、更新、8 条 FAQ）。
> 下面是最短路径。

**Edge**（推荐）：

1. 地址栏打开 `edge://extensions`
2. 左下角打开 **开发人员模式**
3. 点 **加载解压缩的扩展**
4. 选择目录：

```
E:/zzl_workbuddy_datas/招聘agent-build/extension
```

5. 点地址栏右侧拼图图标 → 给「招聘捕手」点**图钉**固定到工具栏

**Chrome**：同样步骤，只是地址换成 `chrome://extensions`。
产物**两边通用**，不需要分别打包。

**装完怎么验证**：点扩展图标，弹出的面板里应显示 🟢 `后端已连接`，
下方能看到「本地待上传队列 / 已入库 / 当前标签页」。
然后打开 BOSS直聘 的简历页，按 F12 看 Console，
出现 `[招聘捕手] 已注入： boss` 和 `[招聘捕手] 捕获到候选人： xxx` 就说明在工作。

**改了代码怎么更新**：`npm run build` → 到 `edge://extensions` 点扩展卡片上的 **🔄 刷新**，
并**刷新招聘网站那个标签页**（content script 只在页面加载时注入）。

### 扩展要连哪个后端？

后端地址是**构建期注入**的，来源是 `.env` 里的：

```ini
VITE_API_BASE=https://your-server.com
```

改完必须重新 `npm run build`，然后到 `edge://extensions` 点扩展卡片上的**刷新**按钮重载。
默认值是 `http://localhost:8787`。

> 改成远程地址时，记得把该域名加进 `apps/extension/manifest.json` 的 `host_permissions`，
> 否则浏览器会拦截上报请求。

> 扩展采集的数据会先存在浏览器本地队列里，后端连不上也不丢，恢复后自动补传。

### 扩展自检与测试

```bash
npm run verify:ext   # 校验产物完整性（manifest 引用的文件是否都在）
npm run icons        # 重新生成图标（改过图形才需要）
npm run test:ext     # 集成测试：自带隔离后端，跑完自动清理
npm test             # 全套：类型检查 + 组件渲染 + 数据层 + 扩展
```

## 看板怎么知道「扩展刚采了新简历」

看板本身不跟扩展通信（一个在网页里，一个在招聘网站的标签页里，跨源发不了消息）。
中间靠后端的数据版本号牵线：

```
扩展采集 → POST /api/capture → 落盘，revision +1
                                      ↑
看板每 5 秒轮询 /api/revision ────────┘
    版本一变 → refreshToken +1 → 六个看台全部重拉数据 → 顶部闪一条「已自动刷新」
```

`/api/revision` 只返回一个自增整数，不碰数据、不算派生视图，轮询成本几乎为零
（这也是为什么不用 `/api/stats` 当探针 —— 它要现算漏斗、简报、人才地图那些派生视图）。

另外，**采集入库时会立刻做一次规则初筛匹配**（`rule-v1`），把简历挂到最对口的在招岗位上。
不做这一步的话新简历没有 `score`，而列表默认按匹配度倒序、无分数的排最后，
新采集的简历会沉到列表最底 —— 观感上就是「我明明采到了，看板却说没有」。

### 历史脏数据怎么修

提取逻辑改进后，**已经入库**的简历不会自动变好。用维护脚本重跑一遍：

```bash
npm run repair:data              # 预览（默认，不动任何数据）
npm run repair:data -- --write   # 执行，先备份到 <数据目录>/_backup/<时间戳>/
```

它会：① 按当前规则重跑字段粗提取（姓名/城市/学历/手机号/邮箱）→ ② 合并重复档案
→ ③ 给仍无岗位匹配的候选人补规则匹配。三步顺序不能反，脚本里有说明。

## 部署到一台新服务器：清单

**要拷的**：`招聘agent-build/` 整个目录（或按分体部署拆开拷）

**要装的**：Node.js ≥ 20（不需要 npm install、不需要 Docker）

**要配的**：

| 配置 | 位置 | 说明 |
|---|---|---|
| 监听端口 | 环境变量 `SERVER_PORT` | 默认 8787 |
| 前端静态目录 | 环境变量 `WEB_DIST` | 一般不用设，会自动找同级 `web/` |
| 扩展上报地址 | 构建期 `.env` 的 `VITE_API_BASE` | 改完要重新 build |

**启动**：`node server/index.js`

## 验收自检

产物起起来之后，逐条敲一遍，全绿就说明部署没问题：

```bash
# 1. 看板首页 → 200 text/html
curl -I http://127.0.0.1:8787/

# 2. 接口正常 → {"ok":true,...}
curl http://127.0.0.1:8787/api/health

# 3. 前端路由回退 → 200（不是 404）
curl -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8787/candidates/123

# 4. 不存在的接口 → 404
curl -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8787/api/nope
```

> 本机如果配了系统代理，curl 访问 localhost 可能报 `upstream connect failed`，
> 加 `--noproxy '*'` 即可。

## 常见问题

### Q1：双击 `web/index.html` 打不开 / 页面空白

正常现象。前端资源用的是绝对路径 `/assets/...`，并且需要后端提供 `/api`。
必须通过服务访问（方式一或方式二），不能直接双击文件打开。

### Q2：启动日志说「未找到前端构建产物，当前仅提供 API」

说明 `server/index.js` 旁边没有 `web/`。检查目录结构是不是被拆散了——
`web/` 必须和 `server/` 同级。也可以手动指定：

```bash
WEB_DIST=/path/to/web node server/index.js
```

### Q3：改了 `.env` 但没生效

- `.env` 只在 **构建时** 被读取（`npm run build`），所以改完要重新构建
- 运行时的 `SERVER_PORT` 是进程环境变量，`npm run start` 会带上

### Q4：产物能瘦身吗？

可以去掉 sourcemap。在各构建配置里关掉 `sourcemap` 即可
（`apps/web/vite.config.ts`、`apps/server/build.mjs`、`apps/extension/build.mjs`），
现在 `.map` 文件比产物本身还大（仅用于调试定位）。

### Q5：端口被占用

```bash
netstat -ano | findstr :8787
taskkill /PID <PID> /F
```
