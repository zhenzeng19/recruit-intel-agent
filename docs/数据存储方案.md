# 数据存储方案

> 回答一个问题：**后端的数据放哪里，比较合适。**
> 结论先给，理由和代价跟在后面。

---

## 一、结论：分三层，按「当前阶段」和「数据性质」分开放

| 层 | 存什么 | 放哪里 | 什么时候用 |
|---|---|---|---|
| **① 结构化数据** | 候选人、岗位、匹配、来源 | **现在**：本地文件库，落盘到仓库**同级**的 `招聘agent-data/`<br>**上线**：托管云数据库（cloud-service / Postgres） | 现在就用①的本地形态，上线时换①的云端形态 |
| **② 简历原件** | PDF / Word 离线简历、BOSS 页面快照、canvas 截图 | 对象存储（OSS / S3 / 云服务自带 Storage） | 等要保存原件时开 |
| **③ 派生数据** | 匹配打分、模型摘要、向量 | **不单独存**，落在①的 `matches` 表里 | 现在就够 |

一句话：**结构化数据本地文件 → 云端数据库；文件走对象存储。** 现在是本机自测阶段，所以先用①的本地形态，零依赖、能直接跑、出问题肉眼可查。

---

## 二、为什么现在不直接上云

你现在要的是「**能不能用**」，不是「能不能扛量」。直接上云会引入三个和当前目标无关的成本：

- **要先把云服务接好才能看到第一条数据** —— 现在本地文件库随起随用，`npm run start` 就有 22 份简历。
- **调试要跨网络** —— 本地文件出错能直接打开看，云库得进控制台。
- **schema 还会变** —— 表结构在 P0→P1 之间必然反复改，本地改了立刻生效，云库每次都要迁移。

但架构上**没有把路堵死**：仓储层已经和存储介质解耦了，换云库是替换一个实现，不是重写。

---

## 三、为什么数据不放进源码仓库

| | 放仓库内（`招聘agent/data/`） | 放仓库同级（`../招聘agent-data/`）✅ |
|---|---|---|
| 会不会被 git 跟踪 | 要额外配 gitignore，容易误提交 | 物理上就在仓库外，**不可能误提交** |
| 简历里有个人隐私信息 | 有泄露到远端仓库的风险 | 天然隔离 |
| `npm run clean` 清产物 | 要额外判断，别把数据一起清了 | 影响不到 |
| 备份 | 跟代码混在一起 | 独立目录，`cp -r` 即为备份 |

简历是**个人敏感信息**，一旦误推到远端仓库就是数据泄露事故。用「物理隔离」而不是「靠 gitignore 兜底」，是这里唯一正确的选择。

> 当然，如果你更习惯数据放在仓库内（比如想跟代码一起打包），把 `.env` 里的 `DATA_DIR` 改成 `data` 即可，`.gitignore` 已经预先忽略了它。

## 四、数据目录长什么样

当前实际落盘结构：

```
E:/zzl_workbuddy_datas/
├── 招聘agent/              ← 源码（git 仓库）
├── 招聘agent-build/        ← 编译产物
└── 招聘agent-data/         ← 【数据】运行时数据，不入 git
    ├── candidates.json     候选人（一人一档）
    ├── positions.json      岗位 + JD
    ├── matches.json        匹配结果 + 推进进度
    └── sources.json        简历来源（去重与溯源依据）
```

一个文件 ≈ 一张表，命名与云端表名一致。打开就能读，方便人工核对：

```jsonc
// candidates.json —— 每条是一个候选人
[
  {
    "id": "cand_seed_001",
    "name": "陈亦舟",
    "city": "深圳",
    "degree": "硕士",
    "school": "华中科技大学",
    "yearsOfExperience": 8,
    "currentCompany": "中科飞测",
    "currentTitle": "资深算法工程师",
    "skills": ["Python", "C++", "OpenCV", "Halcon"],
    "resumeText": "……（简历正文）",
    "parseState": "parsed",
    "createdAt": "2026-09-29T11:23:00.000Z"
  }
]
```

**写盘是原子的**：先写 `xxx.json.tmp`，再 `rename` 覆盖。中途掉电或进程被杀，不会留下半个损坏的 JSON。

## 五、数据目录的位置怎么定（三级优先级）

你不用记，但知道规则在排查时有用：

| 优先级 | 规则 | 适用场景 |
|---|---|---|
| 1 | 环境变量 `DATA_DIR`（相对路径以**仓库根**为基准） | 部署时显式指定；`.env` 里默认写了 `../招聘agent-data` |
| 2 | 从启动目录向上逐级查找已存在的 `招聘agent-data/` | 开发态直接跑 TS 源码时命中 |
| 3 | 相对启动目录的 `../../招聘agent-data` | 产物形态：`招聘agent-build/server/` → 上一级的 `招聘agent-data/` |

> ⚠️ 第 1 条的相对路径**以仓库根为基准，不是进程 cwd**。
> 因为 `npm run dev:server`（cwd = `apps/server`）和 `npm run start`（cwd = 仓库根）的 cwd 不同，
> 如果按 cwd 解释，同一份配置会落到两个不同目录 —— 这个坑开发时已经踩过并修掉了。

启动时终端会明确打印落在哪：

```
招聘情报 Agent 已启动：http://localhost:8787
数据目录：E:\zzl_workbuddy_datas\招聘agent-data
配置文件：E:\zzl_workbuddy_datas\招聘agent\.env
看板入口：http://localhost:8787/
```

## 六、四张表的结构

与 `packages/shared/src/index.ts` 里的类型一一对应，三端共用同一份定义。

### `candidates` —— 候选人（一人一档）
| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `name` / `gender` / `age` / `city` | 基本信息 |
| `degree` / `school` / `major` | 教育背景 |
| `yearsOfExperience` | 工作年限 |
| `currentCompany` / `currentTitle` | 当前任职 |
| `expectedSalary` / `intention` | 期望薪资 / 求职意向 |
| `phone` / `email` | 联系方式（**脱敏存储**） |
| `skills[]` | 技能标签 |
| `summary` | 模型生成的摘要 |
| `resumeText` | 简历正文（文本型来源） |
| `parseState` | `raw` 仅采集原文 / `parsed` 已结构化 |

### `positions` —— 岗位 + JD
`title` / `department` / `city` / `headcount` / `jdText` / `hardRequirements[]` / `niceToHave[]` / `status`

### `matches` —— 候选人 × 岗位
| 字段 | 说明 |
|---|---|
| `candidateId` + `positionId` | 联合定位一条匹配 |
| `score` | 匹配度 0–100 |
| `hitPoints[]` / `missPoints[]` | 命中点 / 缺失点（**可核对，不是黑盒**） |
| `status` | 该候选人在该岗位下的推进进度 |
| `modelVersion` | 打分模型版本，便于回溯 |

### `sources` —— 简历来源
| 字段 | 说明 |
|---|---|
| `candidateId` | 归属候选人 |
| `platform` | `boss` / `liepin` / `offline` / `other` |
| `platformCandidateId` | **平台内 ID —— 去重主键** |
| `resumeUrl` / `capturedAt` | 原页链接 / 采集时间 |

**去重规则**：`(platform, platformCandidateId)` 唯一。同一份简历重复采集只刷新时间，不会产生重复档案；同一人在 BOSS 和猎聘出现则是两条 source、一个人。

## 七、将来换云数据库，要改什么

只有两处，都在 `apps/server/src/db/`：

1. **写一个新的实现类**，实现和 `JsonStore` 相同的方法签名：

   ```
   query(q)              → 检索候选人
   detail(id)            → 候选人详情
   listPositions()       → 岗位列表
   stats()               → 统计聚合
   updateMatchStatus()   → 更新推进进度
   ingestCapture(p)      → 采集入库（含去重）
   seed() / isEmpty()    → 初始化
   ```

2. **在 `apps/server/src/index.ts` 里按 `DATA_DRIVER` 环境变量选择实现**，路由代码一行不动。

之所以能这么干净，是因为路由层只依赖这组方法，从不直接碰文件系统。

### 迁移顺序建议
```
本地文件库  →  （可选）本地 SQLite  →  云数据库 Postgres
```
中间的 SQLite 不是必须的。只有当单机数据量到**几万份简历**、或者关键词检索开始明显卡顿时，才需要这一步（SQLite 有全文索引，换成云库前能先验证 SQL 写法）。**在那之前，本地 JSON 完全够用** —— 上千条记录的线性扫描在毫秒级。

### `cloud-service` 接进来之后，对应的位置
| 本地 | 云端 |
|---|---|
| `candidates.json` | `candidates` 表 |
| `positions.json` | `positions` 表 |
| `matches.json` | `matches` 表 |
| `sources.json` | `sources` 表 |
| `resumeText` 字段 | 表里只留摘要，正文放对象存储，存 key |

## 八、配套的运维事项

### 备份
数据全在一个目录里，`cp -r` 就是完整备份：
```bash
cp -r "E:/zzl_workbuddy_datas/招聘agent-data" "E:/backup/招聘agent-data-$(date +%Y%m%d)"
```

### 重置
看板左侧「重置示例数据」按钮，或：
```bash
curl -X POST http://localhost:8787/api/admin/reset
```
> ⚠️ 会清掉**全部**候选人（包括你手动采集进来的），重新灌入 22 份示例简历。

### 采样数据长得太像真的了
示例数据里的姓名、手机号、邮箱**全部是虚构的**，手机号也已按真人的方式打码（`138****1234`）。但仍建议：**别把示例数据当成真实候选人信息去沟通。**

### 合规红线（大公司尤其注意）
- 只采「你已登录、页面上肉眼可见」的内容，不绕过风控、不做多账号、不批量打招呼
- 简历里的手机号 / 邮箱默认脱敏存储
- 上线前补：**行级权限隔离**（团队用时，各人只看自己负责的岗位）+ **操作审计日志**
- 设定**数据保留期限**：候选人淘汰后 N 个月自动清理，避免无限期留存个人数据

## 九、容量边界（什么时候必须换）

| 规模 | 本地 JSON 是否够用 | 说明 |
|---|---|---|
| < 1,000 份 | ✅ 完全够 | 检索毫秒级，你现在的阶段 |
| 1,000 – 20,000 份 | ⚠️ 够，但开始钝 | 每次查询全量扫描 + 内存索引；单文件涨到几十 MB |
| > 20,000 份 或 多人同时用 | ❌ 必须换 | 单机文件无法处理并发写；需要云库 + 行级权限 |

**另外三个必须上云的信号**（跟数据量无关）：
1. 团队一起用，需要各自的数据权限
2. 换设备 / 手机也想看看板
3. 需要 7×24 在线，不能依赖你本机开机
