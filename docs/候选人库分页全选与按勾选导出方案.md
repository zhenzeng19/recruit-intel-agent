### 过程中修掉的两个真 bug

1. **翻页不生效**（只有真的点按钮才会暴露）
   改了 `fetchCandidates(listQuery)` 却漏改 effect 依赖数组（还是 `[filter]`）。
   后果：点「下一页」时页码与页眉立刻变了（那是从 state 算的），但**列表根本没重新拉** ——
   页眉写「第 21–31 条」、内容还是第 1 页那 20 个人。接口层测试和冒烟测试都抓不到这类问题。
2. **语言筛选口径不一致**
   库里存 `英语(CET6、工作应用)`，下拉要给 `英语`。统一用 `languageKey()` 给
   ①facets 统计 ②筛选比较 两处归一，否则会出现「下拉里有'英语'、选了却筛不出人」。

### 一个刻意的设计取舍

`queryIds`（勾选全部）与 `query`（列表）**共用同一个 `matchRow` 谓词**。
两处各写一遍判断的话，会出现「列表显示 N 人、点『勾选全部』却少选几个」——
而用户完全无从发现。测试里用 9 组条件交叉验证了这个不变量。

## 一、分页（解决「只显示前 50 个」）

**做法**：列表底部加分页条

```
第 1–50 条，共 120 人     [每页 50 ▾]   [上一页]  第 1 / 3 页  [下一页]   跳到 [__] 页
```

要点：
1. **筛选条件一变就回到第 1 页** —— 否则改了条件还停在第 3 页，会看到空列表（这是分页最常见的坑）
2. 每页给 50 / 100 / 200 三档（后端上限 500，200 够用且渲染不卡）
3. **翻页时勾选不丢** —— `picked` 是独立于当前页的集合，天然满足；要验证
4. 页脚的人数文案要如实：**「第 1–50 条，共 120 人」**，而不是只写「命中 120 人」（现在就是后者，所以你会以为只有 50 个）

**改动**：只在前端（`LibraryPage.tsx` 加 `page`/`pageSize` 状态，`filter` 里带上 `limit`/`offset`）。后端不用动。

## 二、勾选全部

**这里有两种语义，都要给，不能只给一种**：

| 按钮 | 含义 | 用途 |
|---|---|---|
| **勾选本页**（50 人） | 只选当前这一页 | 逐页挑人 |
| **勾选全部命中**（120 人） | 选中**所有符合筛选条件**的人（跨页） | 筛完一次性导出 |

再加一个**三态表头 checkbox**：全没选 / 选了部分（显示横杠）/ 本页全选。点一下=勾本页，长按或旁边的小字=勾全部命中。

**实现要点**：需要新增一个**只返回 id 的轻量接口**

```
GET /api/candidates/ids?<与 /api/candidates 相同的筛选参数>
→ { ids: ["c1","c2",...], total: 120 }
```

为什么不能复用 `/api/candidates?limit=500`：
- 服务端 `limit` **上限 500**，命中 800 人时拿不全
- 返回整行数据（含正文摘要）纯属浪费
- 这个接口只回 id，可以让它**不受 500 限制**（几万个短字符串也就几百 KB）

## 三、导出按勾选（Excel + PDF）

### 3.1 Excel

- `api.ts`：`candidateExportUrl(query, preset, ids?)` —— 有 `ids` 时拼 `&ids=a,b,c`
- 服务端 `/api/export/candidates.xlsx`：**接受 `ids`**，给了就只导这些人（忽略筛选条件），并且**保持勾选顺序**
- **UI 文案要跟着变**（避免"我明明勾了却导出了全部"这种困惑）：

| 状态 | 按钮文案 |
|---|---|
| 没勾选 | `导出全部 120 人` |
| 勾了 8 人 | `导出勾选的 8 人` |

### 3.2 PDF：必须同时修掉 50 人上限

`BATCH_LIMIT = 50` 在服务端，改前端没用。建议：

1. **上限 50 → 200**（一次打印 200 份简历是什么概念：约 400–800 页，浏览器扛得住但慢）
2. **超过 50 人时先确认**：
   > 将生成约 480 页 PDF，浏览器可能卡顿几十秒。继续？
3. 页面顶部**如实写明**人数与页数估算
4. 超过 200 人 → 提示**分批导出**（按钮禁用 + 说明），不要静默截断

> 静默截断是最坏的行为：你现在遇到的「只显示 50 个」就是这一类。宁可挡住并说清楚。

## 四、更多筛选条件 —— **需要你确认是哪一种**

你写的是「增加**入库**实现筛选的条件」，我读出两种完全不同的做法，成本差很多：

### (a) 候选人库里加更多**筛选维度**（我猜是这个）

按你已有的字段，可以加的：

| 维度 | 数据来源 | 现成吗 |
|---|---|---|
| 城市 | `candidate.city` | ✅ 已有字段 |
| 学历层次（专科/本科/硕士/博士） | `degree` | ✅ |
| **是否统招** | `educationMode` | ✅ |
| 院校层次（985 / 211 / 双一流） | `schoolTier` | ✅ |
| 年龄区间 | `age` | ✅ |
| 工作年限区间 | `yearsOfExperience` | ✅ |
| 语言（英语/日语…） | `languages` | ✅ |
| 采集方式（自动 / 手动） | `captureMode` | ✅ |
| 采集时间（今天 / 近 7 天 / 自定义） | `capturedAt` | ✅ |
| 有没有联系方式（手机/邮箱） | `phone`/`email` | ✅ |

成本：**中等** —— `CandidateQuery` 加字段 → `store.query()` 加判断 → `FilterPanel` 加控件 → 补测试。一个方向打通，后面加维度都是几分钟。

### (b) **入库时**就按条件筛掉，不让它进库

类似「不再采集名单」的升级版：配一组规则（如"学历低于本科不入库""不在目标城市不入库"），扩展/服务端在**保存前**判断。

成本：**较大** —— 规则存储 + 判定逻辑 + 配置界面。

⚠️ **这个方向有个必须设计好的地方**：判错的代价是**漏采**。人被规则挡掉了，你**不知道他来过**。所以必须配一个**「被规则挡掉的名单」**可查看 + 可恢复，否则你会永远不知道漏了谁。

**我的判断**：从你这段话的上下文（分页 → 全选 → 按勾选导出）看，你要的应该是 **(a)**。但你用了「入库」这个词，所以我不敢直接动手。
