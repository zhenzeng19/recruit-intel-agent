## 一、需求拆解

你提的两句话，实际是三个能力：

| # | 你的原话 | 拆出来的能力 | 本质 |
|---|---|---|---|
| 1 | 「增加一个开关，用来决定是否在界面上启用页面上的简历」 | **总开关**：插件在页面上到底采不采 | 把「无感」变成「可控」 |
| 2 | 「我能手动选择浏览的时候」 | **页内浮动按钮**：浏览时就在眼前，不用点工具栏图标 | 把控制点放到视线上 |
| 3 | 「有个按钮来宣示是否保存这份简历同步到本地」 | **逐份决策**：这份存 / 这份不存 | 把「自动」补上「人工兜底」 |

**当前状态**：三个能力**一个都没有** —— 现在只要页面上被判定成简历就无条件上报（`content.ts:65-91`），用户全程无法干预、也没有任何可见反馈。

**设计目标（按优先级）**

1. 默认行为**不变**（升级后不会突然少采或多采），新能力都是可选的
2. 改开关**立即生效**，不需要刷新页面
3. 手动保存要能救「自动没抓到」的场景（这是最有价值的兜底）
4. 不能因为引入人工交互而破坏现有的去重、断网不丢、诊断能力

## 二、方案总览

### 2.1 用「一个三态模式」代替「两个开关」

**不采用**两个独立开关（`自动采集` + `保存前询问`），因为会产生 `自动=开 / 询问=开` 这种语义冲突的非法组合。

**采用单一枚举**：

```
captureMode: 'auto' | 'confirm' | 'off'

auto    识别到简历 → 静默入库（页面上只留一个收起的小圆点 + 手动补采）
confirm 识别到简历 → 页面上弹卡片问「保存 / 这次不存」，不点不存  ← ✅ 已拍板：默认值
off     完全不采集（页面零打扰，但 __ria 诊断仍可用）
```

一个控件就覆盖了「总开关」（off）和「逐份决策」（confirm）。

> ⚠️ **默认 `confirm` 带来的硬约束**：Step 1（只有开关、没有卡片）单独上线会导致
> **什么都采不到，而且没有任何保存入口** —— 因为默认模式是 confirm、而 confirm 的
> 交互载体（页内卡片）属于 Step 2。所以 **Step 1 与 Step 2 必须同一次做完再交付**，
> 不能分两次发给你。

### 2.2 三个控制面（同一份状态，三处入口）

| 控制面 | 位置 | 作用 |
|---|---|---|
| **页内浮动卡片** | 页面右下角（Shadow DOM 隔离，可拖拽/收起） | 主入口。`confirm` 时是询问卡；`auto` 时是极简状态点 + 手动补采按钮 |
| **扩展 popup 面板** | 点工具栏图标 | 切模式、看当前页识别结果、手动保存、看最近决策 |
| **Console API** | `__ria.save()` / `__ria.skip()` / `__ria.settings()` | 排障与我远程指导时用 |

三处读写**同一份** `chrome.storage.local.capture_settings`，用 `chrome.storage.onChanged` 实时互相同步 —— 所以「在 popup 里改了模式，页面上的卡片立刻变形态」，不用刷新。

## 三、详细设计

### 3.1 状态与协议

**新增共享类型**（`packages/shared/src/index.ts`）

```ts
export type CaptureMode = 'auto' | 'confirm' | 'off'

export interface CaptureSettings {
  mode: CaptureMode
  /** auto 模式下是否显示极简状态点（默认 true，收起成小圆点） */
  showStatusChip: boolean
  /** 卡片被拖到哪儿了（记住位置） */
  cardPos?: { right: number; bottom: number }
  /** 「本页暂停」：origin+pathname → 过期时间戳 */
  pausedPaths: Record<string, number>
  /** 列表页（如猎聘 /recommend）策略：'skip'=不自动采 | 'manual'=降级为手动 | 'normal'=照常 */
  listPagePolicy: 'skip' | 'manual' | 'normal'
}

export const DEFAULT_CAPTURE_SETTINGS: CaptureSettings = {
  mode: 'confirm',       // ✅ 已拍板：默认「保存前询问」，每份简历由你点头才入库
  showStatusChip: true,  // ✅ 已拍板：auto 模式下也显示，但默认收起成小圆点
  pausedPaths: {},
  listPagePolicy: 'manual',
}
```

> **默认值从 `auto` 改成 `confirm` 的影响面**（必须在交付说明里写清楚）：
> ① 升级后第一次打开简历，页面上会冒出询问卡片 —— 这就是新行为，不是你操作错了；
> ② 想让插件回到「无感自动」，在 popup 里切到「自动」即可（一步，且立即生效）；
> ③ **现有自动化测试会受影响**：`tools/test-background.mjs` 里断言「采集后自动入库」的用例，
> 必须先在测试里 `SET_SETTINGS {mode:'auto'}`，否则默认 confirm 会让它压根不入队。
> 这不是测试写错了，而是默认行为真的变了 —— 要显式声明每种测试用哪种模式。

存 `chrome.storage.local` 的 `capture_settings` 键。**content script 直接读 storage**（`storage` 权限已有，content script 可用 `chrome.storage`），不走消息往返 —— 页面加载零延迟，且免费获得 `onChanged` 实时推送。

**消息协议改动**（`background.ts`）

| 消息 | 方向 | 说明 |
|---|---|---|
| `GET_SETTINGS` | 新增 | 回 `CaptureSettings`（合并默认值） |
| `SET_SETTINGS {patch}` | 新增 | 合并写入 + 广播 |
| `SKIP {signature, scope}` | 新增 | `scope: 'once'`=只这份 / `'path'`=本页都别再问 |
| `GET_LOG` | 新增 | 最近 N 次决策（给 popup 的「最近决策」列表） |
| `CAPTURE {payload, source}` | **改** | `source: 'auto'\|'manual'`；**从「发射后不管」改为有回包** `{saved, queued, candidateId?, duplicated?, reason?}` |

> ⚠️ `CAPTURE` 改回包是**破坏性协议改动**（现在 `return false`，`background.ts:168-201`）。必须单独一步做，并同步改 `tools/test-background.mjs` 里相关断言。改它的理由：手动保存必须给用户真实回执（「已保存」/「后端没连上，已排队(1)」），没有回包就只能骗用户。

**SKIP 的落点**：`skipped_ids`（`{signature, at}`，最多 200 条，按时间淘汰）+（`scope='path'` 时）写进 `settings.pausedPaths`。
**关键**：「跳过」**不写入 `captured_ids`** —— 否则用户之后想手动存这份时会被自己的「跳过」挡住。

### 3.2 content.ts 重构（实时生效的关键）

```ts
async function bootstrap() {
  applySettings(await getSettings())
  chrome.storage.onChanged.addListener((ch, area) => {
    if (area === 'local' && ch.capture_settings) applySettings(ch.capture_settings.newValue)
  })
}

function applySettings(s: CaptureSettings) {
  if (s.mode === 'off') { teardownObservers(); overlay.hide(); return }  // 彻底停手
  startObservers()                                                       // 幂等
  overlay.render(s.mode, currentOutcome)                                 // 换形态，不重建
}
```

采集判定改成分支：

```ts
const outcome = await waitForResume()                 // 复用现有 12s 轮询
if (!outcome.ok) { overlay.showNoResume(); return }
const sig = signatureOf(outcome.payload)
if (sig === lastSignature || dismissed.has(sig)) return

if (mode === 'auto')    { const r = await sendCapture(outcome.payload, 'auto'); overlay.showSaved(r) }
else if (mode === 'confirm') { overlay.ask(outcome.payload, { onSave, onSkip }) }   // 不自动上报
// off 分支不会走到这里
```

要点：
- `confirm` 模式下**不能**先把 `lastSignature` 置位，否则卡片会被自己的判重压掉 → 用独立的 `askingSignature` 防重复弹卡。
- 页面生命周期内用内存 `dismissed: Set<signature>` 兜住 MutationObserver 的反复触发（持久化的跳过在 background）。

### 3.3 页内浮动卡片（`overlay.ts`，新增文件）

**形态**

| 模式 | 形态 |
|---|---|
| `off` | **不注入任何 DOM**（零打扰） |
| `auto` | 收起成小圆点（默认），hover 展开 →「已自动保存 ✓ 张小雨 · 1,842 字」+ `[手动保存这一页]`。未识别到 → 灰点「未识别到简历」 |
| `confirm` | 展开的卡片：「识别到 **张小雨** · 1,842 字」+ `[保存到看板]` `[这次不存]` `[本页都不再问]` |
| 任意模式 | 后端未连接时显示「已排队(1)，服务起来自动补传」 |

**实现要点（都是踩过的坑对应）**

1. **Shadow DOM 隔离**：`attachShadow({mode:'open'})` + `:host{all:initial}` + 内联样式。不隔离的话猎聘的全局 `font-size`/`reset` 会把卡片搞变形。
2. **挂载点用 `document.documentElement` 而不是 `body`** —— SPA 重渲染可能替换 `body`，挂 body 上会连卡片一起没。
3. **自愈**：用 MutationObserver 检测自己的宿主节点被移除 → 重新挂载（猎聘是重度 SPA）。
4. **位置**：`position: fixed; right/bottom` 从 `settings.cardPos` 读，可拖拽，拖完写回。默认右下角但要避开站点自己的悬浮按钮 → 默认 `right: 20px; bottom: 96px`。
5. **多帧只出一张卡**：`all_frames: true` 下每个帧都会注入。复用**现有 `DIAGNOSE` 的抢答机制**（`content.ts:181-203`）—— 只有 `containerFound === true` 的帧出卡；主框架在「没有任何帧识别到」时才显示状态点。这条已经在生产验证过（解决了主框架的「没找到」带偏结论的问题）。
6. **可关闭**：`showStatusChip=false` 时 `auto` 模式下完全不出卡（只留 popup 入口）。

### 3.4 手动「强制保存」（最有价值的部分）

现状：`findResumeContainer()` 有两道门槛 —— `MIN_RESUME_CHARS=240`、`PASS_SCORE=18`（`extract.ts:148-152`、`231-268`）。门槛是为了**防止自动采集存脏数据**，但代价是「页面确实是简历、只是写法不标准」时会漏采，而用户无从补救。

**手动保存时放宽门槛**（新增 `extractForced()`）：

- 复用 `findResumeContainer()` 的候选排序逻辑，但**去掉 `PASS_SCORE` 门槛**，只保留 `240 ≤ len ≤ 60000`
- 拿不到候选 → 回退 `document.documentElement.innerText` 截断 60000 字，但**必须二次确认**（因为可能抓到整页）
- payload 标记 `source: 'manual'`、`lowConfidence: true`
- 回执里**显式告知不确定性**：
  - ID 来自内容指纹（`content:xxx`）时提示「未识别到平台 ID，已按内容指纹建档，可能与历史记录重复」
  - 字数偏低时提示「正文偏短（320 字），可能不完整」

> 这条设计的取向是：**宁可把不确定性摊开给用户看，也不偷偷存一条脏数据**。人力介入的场景本来就应该由人负责判断。

### 3.5 列表页护栏（针对你给的 `/recommend`）

你给的 `https://lpt.liepin.com/recommend` 是**人才推荐列表页** —— 这是当前实现的一个**真实风险点**：列表页上一堆候选人卡片，聚合起来的文本很可能同时满足「正文 > 240 字」和「命中 ≥2 个章节词」，被启发式**误判成一份简历**，存进一条包含多个人的脏数据。

**两层护栏**

1. **路径清单（确定性高，快路径）**：`SITES.liepin` 增加
   ```ts
   listPaths: [/\/recommend/, /\/search/, /\/talent/, /\/candidate\/list/]
   ```
   命中时按 `settings.listPagePolicy` 处理：`manual`（默认）= 不自动采，只在卡片上提示「检测到列表页，已跳过自动采集；点开某位候选人的简历再保存」；`skip` = 完全不出卡；`normal` = 照常（给需要的人）。

2. **聚合容器检测（兜底，站点换 URL 也挡得住）**：新增 `looksLikeListContainer(text)` —— 在一份候选容器里数「多人特征」：
   - `/(\d{1,2})\s*岁/g` 出现次数
   - 「查看大图 / 意向沟通 / 继续沟通」出现次数
   - 手机号匹配数
   - 「工作 N 年」出现次数

   若 **≥2 种特征各出现 ≥3 次** → 判定为聚合容器，自动采集拒绝（`reason:'aggregate-container'`），手动保存时给用户明确选择「仍要保存这一整块」。

**但我需要你先做一件事才能定死这层**：在 `/recommend` 上跑一次诊断（见第五节），因为「简历是点开后右侧面板出现」还是「卡片里内联展示」决定了护栏的具体形态。

## 六、已拍板的决策（2026-10-05）

| # | 问题 | 拍板结果 |
|---|---|---|
| 1 | **默认模式** | ✅ **`confirm`（保存前询问）** —— 每份简历由你点头才入库 |
| 2 | `auto` 模式下页面上要不要状态点 | ✅ **要，但默认收起成小圆点**（hover 才展开） |
| 3 | 「不存」的粒度 | ✅ **三级都要**：`这次不存` / `本页都不再问` /（切到）`关闭` |
| 4 | 未达阈值时允许强制保存吗 | ✅ 允许；**只在「回退到整页文本」这种最坏情况要二次确认**（其余靠回执里提示不确定性） |
| 5 | `/recommend` 这类列表页策略 | ✅ **`manual`**：不自动采，但允许你手动保存点开的那一份 |
| 6 | 后端加 `captureMethod` 字段 | ✅ **加**（`source` / `lowConfidence` / `captureMethod` 三个可选字段） |

**由 #1 派生的两条硬约束**

1. **Step 1 与 Step 2 必须同一次交付**（理由见 §2.1 的警告）
2. **`test-background.mjs` 需要显式声明模式** —— 现有断言默认是「自动入库」，默认值改成
   `confirm` 后这些断言会失败。正确处理是在用例开头 `SET_SETTINGS {mode:'auto'}`，
   而不是偷偷把测试改成「跳过断言」

## 七、风险与权衡（review 时值得看的）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 注入 DOM 被站点重渲染冲掉 | 猎聘是重度 SPA | Shadow DOM + 挂 `documentElement` + `MutationObserver` 自愈重挂 |
| 卡片遮挡站点自己的悬浮按钮 | 右下角常有客服/反馈入口 | 默认 `bottom: 96px` 让位 + 可拖拽记忆 + 可收成圆点 |
| `all_frames` 下多处出卡 | 每个帧都注入 | 复用已验证的「有容器的帧抢先应答」机制，只出一张 |
| 强制保存产生脏数据 | 内容指纹 ID 不稳定 | 回执显式提示不确定性；后端 `(platform, id)` 去重兜底；`lowConfidence` 落库可事后筛出 |
| `CAPTURE` 改回包影响现有测试 | test-background 可能断言了旧行为 | 单独 Step 1 做，同步改断言并跑全测 |
| 「跳过」把用户自己的手动保存挡了 | 若跳过也写 `captured_ids` 就会 | **跳过只写 `skipped_ids`，绝不写 `captured_ids`** |
| SW 被回收后开关状态丢失 | MV3 常事 | 设置存 `chrome.storage.local`（持久化），不是内存态（对比 `capture_state` 曾踩过这个坑） |
| 列表页脏数据 | 你刚给的这个页面就是 | Step 3 两层护栏 |
| 隐私口径 | 手动保存是更强的用户授权 | `captureMethod` 落库，来源可追溯 |

## 八、不做的事（明确排除，避免范围蔓延）

- ❌ 不做「多账号 / 批量翻页 / 无人值守高频采集」（合规红线，见总览方案 §9）
- ❌ 不做「按站点分别设开关」（先用全局 + 「本页暂停」覆盖 90% 场景；确有需要再说）
- ❌ 不引入任何 UI 框架（卡片是几十行原生 DOM + 内联 CSS，与项目「零额外依赖」的取向一致）
- ❌ 不改现有判重主键 `(platform, platformCandidateId)` 与内容签名机制
- ❌ 不动看板六个页面的现有结构（只可能在抽屉里加一行「采集方式」）
