## 零、先看你真实数据的体检结果（用证据定位问题，别猜）

我用你**真实采集的 3 份简历**（张小雨、孙先生、李先生）逐字段对了一遍。结论是：**问题不在「抓不到」，而在「抓的方式不对」**。

| 字段 | 现状 | 根因（已定位到代码） |
|---|---|---|
| **学校 / 专业** | ❌ 三条全空 | `parseResumeText()` **根本没有这两个字段的提取逻辑** —— 但它们在正文里 |
| **统招 / 非统招** | ❌ 三条全空（这正是你说的「招聘软件识别不了」） | 同上，**没有这个字段**；而猎聘**已经标好了**：`… · 本科 · 统招` / `… · 本科 · 非统招` |
| **性别** | ❌ 三条全空 | 没有提取逻辑。猎聘头部**没有**「性别：」标签，但名字是「孙先生 / 李先生」→ 性别就在称呼里 |
| **工作年限** | ❌ 三条全空 | **确凿 bug**：`store.ts` 用 `/(\d{1,2})\s*年(?:工作)?经验/` **要求「经验」二字**，而猎聘写的是 `工作2年` / `工作17年` / `工作15年` → 不匹配。讽刺的是 `match-rule.ts` 的 `yearsOf()` 用的是 `/(?:工作\|经验\|从业)[^\d]{0,6}(\d{1,2})\s*年/` **能匹配** —— 同一份代码里两个正则不一致 |
| **城市** | ⚠️ 2 条对、1 条空 | 李先生正文第 7 行明写 `盐城`，但 `CITY_LIST` 只有 55 个城市、**没有「盐城」**，且没有「不依赖词典」的兜底 |
| **薪酬** | ✅ 基本能用 | `6-7k` / `30-40k` / `26-27k` 都抓到了；但 `7k×13薪` 这种「单值 + 13 薪」写法只抓到前面的 `7k`，**年包信息（×13）丢了** |
| **当前公司** | ⚠️ 抓到了但可能不是「当前」 | 用「含『有限公司』且 ≤30 字的首行」→ 可能抓到**工作经历里的任意一家**，而不是当前这家 |
| **技能 tags** | ❌ 三条全空 | 没有提取逻辑 → 结果：**人才 Map 的技能云对真实数据是空的**（只有 22 份种子数据有） |
| **经历摘要** | ❌ 是占位文案「待大模型结构化」 | 需要 LLM（P1-b）；规则能做一版粗摘要 |
| **岗位归属** | ⚠️ 三条被规则挂到了 `pos_cpp`（40/55 分） | 它们的正文第 1-2 行写着 `推荐职位：项目经理` —— **猎聘自己告诉我们该挂哪了**，而我们的规则分只能瞎猜（你岗位里没有「项目经理」） |

### 最关键的一条洞察

**猎聘的头部是「裸行 + · 分隔」格式，而我们的提取器是「标签驱动」的** —— 两者根本对不上。看真实头部：

```
推荐职位：              ← 猎聘给的岗位线索（我们完全没用）
项目经理
发起意向沟通
查看大图
孙先生                  ← 姓名（含称呼 = 性别线索）
更新简历时间：…
北京                    ← 城市（裸行，无标签）
工作17年                ← 工作年限（裸行）
39 岁                   ← 年龄
离职，正在找工作
某某工业大学 · 土木工程 · 本科 · 统招     ← 学校 · 专业 · 学历 · 统招（一行四个字段）
工作背景：拥有16年基建项目全周期管理经验…   ← 经历摘要（可做粗摘要）
```

目前 `parseResumeText()` 找的是 `性别：男`、`毕业院校：X`、`现居：X` 这类**带标签**的行 —— 种子数据（我造的）是那个格式，所以你之前的测试全绿；**真实猎聘页面不是那个格式**，于是标签找不到，字段全空。

> 这不是小修补能解决的，得把提取器从「标签驱动」升级为「**头部区块 + 三种证据**」。

## 一、字段增强：引入「头部区块 + 三种证据」

### 1.1 核心改动：先把正文切成「头部」和「章节」

**头部** = 从第 1 行到第一个章节词行（`工作经历` / `教育经历` / `【技能标签】` / `求职意向` …）之间。
**章节区** = 之后的部分。

为什么这一步是根因修复：头部是**结构化的字段区**（姓名/年龄/城市/学历/薪资在一小段里），往下是**自由文本区**（工作经历里的公司名、项目名什么都可能出现）。现在 `extractCity()` 用「`N 岁` 锚点 ±2 行」来凑合这件事，`currentCompany` 靠「含『有限公司』的首行」猜 —— 都是在缺这个切分的情况下打补丁。

切分后，**所有字段提取只在头部内做**（少数需要全文的除外，比如技能标签）。这一刀能同时修掉「城市抓错」「公司抓错」两个老问题。

### 1.2 头部内按三种证据依次提取

| 证据级别 | 形态 | 例子 |
|---|---|---|
| **① 显式标签**（最可靠） | `标签：值` | `性别：男`、`现居：深圳`、`期望薪资：30-50k` |
| **② 分隔符行**（猎聘主力格式） | `A · B · C · D` | `某某工业大学 · 土木工程 · 本科 · 统招` |
| **③ 位置 / 称呼规则** | 裸行、锚点邻域 | `工作17年`、`39 岁`、`北京`、`孙先生` |

**分隔符行的拆解规则**（一行出四个字段，性价比最高）：

```
某某工业大学 · 土木工程 · 本科 · 统招
   ↓ 按 · ｜ | ／ / 切段
   ├─ 含 大学/学院/研究院/学校   → school
   ├─ 命中 学历词表（博士/硕士/本科/大专…）→ degree
   ├─ 命中 统招词表              → educationMode
   └─ 其余非空段                 → major
```

### 1.3 新增 / 修复的字段清单

| 字段 | 取值 | 来源与规则 |
|---|---|---|
| `gender`（启用现有字段） | `M` / `F` / `unknown` | ① `性别：男` ② **称呼**：`X先生`→M、`X女士/X小姐`→F ③ 头部裸行 `男`/`女` ④ 否则 unknown |
| `school` | 文本 | 标签 `毕业院校/学校/院校` → 分隔符行里含 `大学/学院/研究院` 的段 |
| `major` | 文本 | 标签 `专业` → 分隔符行的剩余段 |
| `educationMode`（**新增**） | `统招` / `全日制` / `非统招` / `非全日制` / `自考` / `成人教育` / `网络教育` / `专升本` / `函授` / `夜大` / `未知` | 头部与全文匹配统招词表。**归一化**：`统招` 与 `全日制` 统一成 `统招`（语义等价），`非统招`/`非全日制`/`自考`/`成人`/`网络教育`/`函授`/`夜大` 统一成 `非统招`，`专升本` 单独保留（它是学历路径不是统招属性） |
| `educationEvidence`（**新增**） | 原文片段 | 存下命中的那一行，**便于你在看板上核对**（这一条很重要：机器判断学历性质必须可追溯） |
| `yearsOfExperience` | 数字 | **修 bug**：统一用 `match-rule.ts` 那版正则，支持 `工作N年` / `N年工作经验` / `从业N年` |
| `city` | 文本 | ① 标签（排除「期望城市」）② 锚点 `N 岁` / `工作N年` ±2 行内命中**扩充后的城市词典** ③ **新兜底**：锚点邻域内的「短中文行」（2–4 字、不含数字/标点）当作候选，再与词典交叉验证 |
| `expectedSalary` | 文本 | 现有正则 + 支持 `7k×13薪` → 存成 `7k×13`（年包信息别丢） |
| `currentTitle` | 文本 | 标签 `当前职位` → 头部里末段的职位词 → `求职意向` 行 |
| `intention` | 文本 | 标签 `求职意向` → 头部的职位意向行 |
| `currentCompany` | 文本 | **优先头部**标签 → 头部里含公司后缀的行 → 兜底：**第一段工作经历的第一行**（比「全文任意一行」准得多） |
| `skills`（**新填充**） | 字符串数组 | 用 `match-rule.ts` 现成的 `TECH_TERMS`（约 150 个行业术语）当词典扫全文。**零成本让人才 Map 的技能云对真实数据也有内容** |
| `schoolTier`（**新增，可选**） | `985` / `211` / `双一流` / `''` | 文本里显式出现，或命中内置的 985/211 院校名单（约 150 所）。**HR 筛简历时这个比学历本身还常用** |
| `recommendedPosition`（**新增**） | 文本 | 猎聘头部的 `推荐职位：X`。三个用途：① **保存时选岗的默认值** ② 看板上显示「猎聘推荐：项目经理」帮你判断 ③ 将来做岗位自动归类的强特征 |

### 1.4 字段提取放在哪一层？（这是个必须明确的设计决策）

**放服务端 `parseResumeText()`，扩展侧只送 `rawText`。** 理由：

1. **历史数据能重跑**：`parseResumeText` 是导出的，`npm run repair:data --write` 会用新规则把**已入库的简历**重跑一遍 —— 你现在这 3 条脏数据（field 全空）**改完就能一键修好**，不用重新采集。这是项目里已经验证过的机制（当年修「姓名被抓成『查看大图』」就是这么修的）。
2. **一处维护**：扩展轻、解析重，改规则不用重新装扩展。
3. **可单测**：纯函数，能像现在这样在 Node 里跑断言。

> ⚠️ 注意 `repair-data.mjs` 只重跑 `parseState === 'raw'` 的记录 —— 真实采集进来的都是 `raw` ✓，所以我造的 22 份种子数据（`parsed`）不受影响。**但种子数据的学历行是我编的「性别：男 年龄：33 岁」格式，跟真实猎聘格式不同** —— 建议在种子数据里**补几条猎聘格式的样本**（`A · B · 本科 · 统招`），否则新提取器的真实格式分支没有测试覆盖。

### 1.5 「经历」要不要做成摘要？

- **工作年限**：上面已修，会立刻有值。
- **完整工作经历**：正文已经在 `resumeText` 里，看板抽屉能看全文 —— 这条不缺。
- **一句话经历摘要**：`Candidate.summary` 字段早就留好了，但真实数据填的是占位文案。规则能做一版**粗摘要**（当前公司 + N 年 + 最高学历 + 最近一段经历的标题），但真正好用的摘要需要 LLM（P1-b）。**建议：先做粗摘要，别等模型。**

## 二、岗位管理：后台自己加岗位

现在**完全无法新增岗位**（没有 `POST /api/positions`，看板也没有入口），岗位只能靠种子数据 —— 这是你这条诉求的根因。

### 2.1 新增 API

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/positions` | 新建岗位 |
| PATCH | `/api/positions/:id` | 编辑（含改 `status`） |
| DELETE | `/api/positions/:id` | 删除（**有匹配时拒绝**，见下） |
| POST | `/api/rematch` | 按当前岗位重跑规则匹配（给「待匹配」的人补挂） |
| POST | `/api/candidates/:id/matches` | 手动把某人挂到某岗位 |
| DELETE | `/api/candidates/:id/matches/:positionId` | 取消挂靠 |

### 2.2 新页面 `#/positions`「岗位管理」

侧边栏加第 7 个入口。内容：

```
┌────────────────────────────────────────────────────────────┐
│ 岗位管理                        [ + 新建岗位 ]  [ 重跑匹配 ] │
├────────────────────────────────────────────────────────────┤
│ 高级视觉算法工程师（缺陷检测）  [在招]                        │
│ 算法部 · 深圳 · 编制2 · 候选人 6 · 均分 84 · 强推 3           │
│ [编辑] [停用] [删除]                                         │
├────────────────────────────────────────────────────────────┤
│ 应用工程师 / FAE（客户现场）    [已暂停]                      │
│ 应用部 · 深圳 · 编制1 · 候选人 4 · 均分 76                   │
│ [编辑] [启用] [删除]                                         │
└────────────────────────────────────────────────────────────┘
```

**表单字段**：标题\*、部门、城市、招聘人数、状态（在招/暂停/关闭）、JD 正文\*、硬性条件（一行一条）、加分项（一行一条）。

### 2.3 删除 vs 停用（一个必须明确的策略）

- 岗位下**有候选人匹配** → **只允许停用**，不允许删除。理由：删了会让这些人的 `matches` 变成孤儿（代码里只能显示「（岗位已删除）」），数据静默损坏。
- 岗位下**没有匹配** → 允许删除（二次确认）。
- 停用的岗位：`rankPositions()` 只看 `status === 'open'`，所以**停用后不会再被自动挂靠**，但历史匹配和看板展示都保留。

### 2.4 「重跑匹配」为什么值得做

你新建一个岗位后，之前因为「在招岗位都不匹配」而进入**待匹配**的候选人不会自动重新匹配。`store.rematchUnmatched()` **已经写好了**，只是没有 API 入口 —— 接一个按钮就行，成本极低。

## 三、保存时选岗位（核心诉求）

### 3.1 数据流（关键：岗位必须跟着 payload 一起入队）

```
页面卡片 / popup 选择岗位
   ↓ CapturePayload 增加 positionId
background.accept()  ← 原样透传，入队时就带上
   ↓ POST /api/capture { …, positionId }
store.ingestCapture()
   ├─ 有 positionId 且命中在招岗位 → 建 Match { assignedBy:'manual', positionId, score: 该岗位的规则分 }
   └─ 没有 → 走现有 autoMatch()（规则分最高者）
```

> ⚠️ **`positionId` 必须存进本地队列**（`capture_queue`）而不只是放在内存里。否则「后端没起 → 先排队 → 之后补传」这条路径会把选岗信息丢掉。这是本项目「断网不丢」设计的一部分，不能破。

### 3.2 `Match` 增加 `assignedBy`

```ts
assignedBy?: 'rule' | 'manual' | 'pick-from-recommend' | 'model'
```

用途：看板上显示「这个岗位是**你指定的**还是**自动猜的**」，也便于统计规则准确率。比复用 `modelVersion` 语义清晰。

### 3.3 选岗后，规则自动挂的那个怎么办？（**需要你拍板**）

| 方案 | 效果 | 代价 |
|---|---|---|
| A. 删掉规则挂的，只留你选的 | 漏斗最干净 | 丢了「规则原本推荐谁」的信息 |
| B. 两个都留（你选的主 + 规则备选） | 信息全 | 漏斗计数虚高，正是当初 `autoMatch` 只挂一个岗位要避免的问题 |
| **C. 默认 A，但在回执里告知 + 给一键「也挂上」（推荐）** | 干净且信息不丢 | 多一行回执文案 |

**我推荐 C**：卡片回执显示「已保存并挂到『视觉算法』。规则原本推荐『C++ 软件工程师』（55 分），[也挂上]」。

### 3.4 卡片与 popup 的交互

**页内卡片**（`confirm` 模式识别到简历时）：

```
┌──────────────────────────────────────┐
│ 识别到一份简历                        │
│ 孙先生 · 6634 字 · 尚未入库            │
│                                      │
│ 挂到岗位：                            │
│ ┌──────────────────────────────────┐ │
│ │ 项目经理（你还没有这个岗位）  ▾   │ │ ← 下拉，默认值见 3.5
│ └──────────────────────────────────┘ │
│ 猎聘推荐：项目经理                    │ ← 来自 recommendedPosition
│                                      │
│ [保存到看板] [这次不存] [本页都不再问] │
└──────────────────────────────────────┘
```

**popup 面板**里放同样的选择器（空间更大，岗位多时更好用）+ 一行「猎聘推荐职位：X」。

### 3.5 三个让它「不烦人」的设计

1. **记住上次选的岗位**（存 `settings.lastPositionId`）：同一批简历往往属于同一个岗位，每次都选会很烦。卡片默认选中上次的，并显示「上次：视觉算法」。
2. **用 `recommendedPosition` 猜默认值**：猎聘头部写了 `推荐职位：项目经理` → 若你的岗位里能模糊命中（复用 `ask()` 那套 2-gram ≥2 命中），就默认选它；命不中就退化到「上次选的」。
3. **不强制选**：允许留空（=「先按规则自动挂」）。不是每份简历你都想当场归类。

### 3.6 自动模式（`auto`）下怎么办

自动模式下没有打断的机会，所以：

- **保持规则匹配**（现状），但增加一条：**`recommendedPosition` 能在你的岗位里命中时，优先用它**（这是「猎聘自己说的」比「我们猜的」更可信）。
- **看板里提供事后改岗位的入口**（见 3.7）—— 这是自动模式下的兜底，本来就该有。

## 六、需要你拍板的 7 个点

| # | 问题 | 我的建议 |
|---|---|---|
| 1 | `educationMode`（统招/非统招）要不要加？ | **要**。这正是你说的「招聘软件识别不了」的差异点，而且猎聘已经把答案写在正文里了，成本极低 |
| 2 | `schoolTier`（985/211/双一流）要不要顺手加？ | **建议加**。HR 筛简历时它比学历本身更常用，成本只是内置一份院校名单 |
| 3 | `skills` 用 `TECH_TERMS` 词典自动打标？ | **建议要**。零成本让人才 Map 技能云对真实数据有内容；但它是「词典命中」不是模型抽取，语义上要标清楚（比如 `skillsSource: 'dictionary'`） |
| 4 | 选岗后规则自动挂的那个 | **C：默认只留你选的，回执里告知规则推荐 + 一键「也挂上」** |
| 5 | 自动模式下是否用 `推荐职位` 优先于规则分？ | **建议用**。猎聘自己说的比我们猜的可信；命不中再退化到规则分 |
