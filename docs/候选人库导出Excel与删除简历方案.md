> **实施中额外发现并修掉的 3 个真 bug**
> 1. **姓名提取会被城市/学历顶掉**（`guessResumeName` 第 ② 步「往前找 3 行」）。
>    `李先生\n盐城\n工作15年` 解析出的姓名是**「盐城」**；`王五\n深圳\n本科\n30 岁` 是**「本科」**。
>    这会直接污染 Excel 的姓名列。已用「城市词典 + 学历判定 + 状态词」三道排除修掉（`normalizeEducationMode` 返回**空字符串**而非 `null`，写成 `!== null` 会让姓名全空 —— 这个坑也踩了一次）。
> 2. **项目符号行被当成公司名**：非结构化的「工作经历」常常是一串 `1. …` 条目，早先会把第 1 条当公司，
>    导出的「经历」列变成一句描述。已加「项目符号 / 职位名 / 句子」三重排除，并在结构化失败时用 `tidyExcerpt()` 兜底（去编号、在句读处收尾）。
> 3. **`周敏` 在真实数据里确实存了两条档案**（1866 字 / 1851 字）—— 用户从预览面板采了一次、从详情页又采了一次，
>    而当时 `resIdEncode` 还没进 ID 参数表，两次算出的内容指纹不同。**这正是上一轮预测过的重复建档问题，它真的发生了**；
>    `repair:data` 已合并为一条（保留信息更全的、迁移来源）。

## 零、先做数据体检（结论决定方案怎么做）

### 0.1 「语言」这个字段我们现在**根本没存**，而且直接解析出来是脏的

`parseResumeSections().languages` 能解析，但真实数据实测：

| 候选人 | 解析出的「语言」 |
|---|---|
| 孙先生 | `["英语", "普通话"]` ✅ |
| 周敏 | `["英语", "普通话"]` ✅ |
| 李先生 | `["普通话", "简历编号"]` ❌ 混进了噪声 |
| 张小雨 | `["英语(CET6、工作应用)", "日语(N3、基础沟通)", "德语(基础沟通)", "附件简历", "0.4MB", "预览", "下载", "简历编号", "投递时间: 2026.09.30", "通过筛选", "不合适"]` ❌❌ 混进一大串 |

**根因**：`语言能力` 这个章节一直延到正文末尾，后面的 `附件简历` / `简历编号` / 投递按钮都不被识别成章节标题，就全掉进「语言」里了。

**修法（两道防线）**：
1. 语言用**白名单**而不是「取章节里所有行」：只认 `英语/日语/德语/法语/韩语/俄语/西班牙语/葡萄牙语/意大利语/阿拉伯语/泰语/越南语/普通话/粤语/闽南语/上海话` 开头的行，可带括号补充（`英语(CET6、工作应用)` 保留，因为它有信息量）；其余一律丢弃。
2. 章节切分补上尾部标题（`附件简历`、`简历编号`、`投递时间` 等），并在 `语言能力` 章节里最多取 6 条。

→ 同时**给 `Candidate` 加 `languages?: string[]` 字段**（现在只存在解析结果里，没落库）。

### 0.2 「经历」能拿到，但**分块解析有漏**：周敏 4 段工作只认出 1 段

真实数据里 `工作经历` 有两种结尾标记：

| 格式 | 特征 | 分块效果 |
|---|---|---|
| 猎聘**预览面板**（孙先生、李先生） | 每段结尾有 `*该段内容已整合附件简历信息` | ✅ 块切得准 |
| 猎聘**详情页**（周敏） | **完全没有**这个标记 | ❌ 整段被当成 **1 段**，4 家公司塌成 1 条 |

周敏正文里明明有 4 家公司（`某某集团` / `某某半导体科技有限公司` / `某某电子分厂` / `某某电子有限公司`）。

**修法**：在「没有块结束标记」时，**改用「公司名行」当分块边界** —— 一行若短（≤30 字）且含 `公司/集团/研究院/厂/中心/事业部/银行/医院/学校` 等机构词，就认为是一段新经历的开始。
这条不影响已有行为（有标记时仍走标记），只是让没有标记的格式也能切对。

→ 对「经历」这一列的影响很直接：现在只能写 1 家公司，修完能写全 4 家。

### 0.3 `candidate.intention`（求职意向）**5 条真实简历全是空的**，但分节解析能拿到

`parseResumeText` 里的 `extractIntention()` 在猎聘真实格式上取不到值；而 `parseResumeSections().intention` 是好的（孙先生 → 职位 `项目经理/主管`、薪资 `30-40k×12`、城市 `北京/南京/成都/上海/天津/盐城`）。

→ **让两者共用一套实现**（`parseResumeText` 改为复用分节结果），顺手把「期望城市 / 意向职位」喂给导出。

### 0.4 岗位名里有会破坏 Windows 文件名的字符（已实测）

`应用工程师 / FAE（客户现场）` 含 **`/`** —— 直接拿去做文件名会创建失败或变成路径分隔符。
→ 文件名必须做净化：`[\\/:*?"<>|]` → `-`，并去掉首尾空格与点号。

### 0.5 零依赖生成 .xlsx：**已做原型并用 openpyxl 反向验证通过** ✅

`.xlsx` 本质是一个 ZIP + 几个 XML。我用 Node 内置能力手写了一份（store 方式压缩 + `inlineStr`），
然后用 Python 的 **openpyxl** 打开它反向验证：

```
  sheet 名：['推荐名单']        尺寸：A1:I5
  冻结窗格：A2                  自动筛选：A1:I5
  表头是否加粗：True
  年龄是否数字类型：int 38        ← 数字列在 Excel 里能直接排序/求平均
  长文本列宽：60.0
  转义：'含特殊字符 <&"\'>' 与 'A & B < C > D' 原样还原 ✅
```

**结论：可以零依赖生成真正的 .xlsx**（带冻结表头、自动筛选、加粗表头、列宽、数字列）。
比 CSV 好在：CSV 文件名只能是 `.csv`、没有格式、双击时 Excel 有时还要问分隔符。
（原型验证时 openpyxl 报了一个 `Workbook contains no default style` 警告 —— 正式实现里补上 `<cellStyles>` 即可消除。）

**为什么不用现成库**：`exceljs` 之类会给服务端包体加 1~2MB，而**便携包的卖点就是自包含零依赖**；
我们只需要「写一张表」这一个能力，手写 ZIP + XML 约 200 行，还能被 openpyxl 真正验证。

## 一、Excel 导出设计

### 1.1 导出哪批数据

**当前筛选结果的全部**（不只是当前这一页）。也就是复用候选人库现有的查询条件：`q` / `positionId` / `platform` / `status` / `minScore` / `sort`，但**忽略分页**。
上限 5000 条（超过就在文件里写清「只导出了前 5000 条」，因为正常招聘量远达不到）。

### 1.2 列（两套预设，界面上用单选切换）

**「精简」= 你点名的字段 + 必要上下文**

| # | 列名 | 来源 | 说明 |
|---|---|---|---|
| 1 | 姓名 | `name` | |
| 2 | 性别 | `gender` | M/F → 男/女；判不出来**留空**，不猜 |
| 3 | 年龄 | `age` | 数字列 |
| 4 | 学历 | `degree` | 本科/硕士… |
| 5 | **学历性质** | `educationMode` | **统招 / 非统招 / 专升本** ← 你要的重点 |
| 6 | 毕业院校 | `school` | |
| 7 | 院校层次 | `schoolTier` | 985 / 211 / 双一流 |
| 8 | 专业 | `major` | |
| 9 | 工作年限 | `yearsOfExperience` | 数字列 |
| 10 | 经历 | 分节结果摘要 | `公司·职位(起止)`，多段用 `；` 连接（见 §0.2 修复） |
| 11 | 薪酬 | `expectedSalary` | |
| 12 | 所在城市 | `city` | |
| 13 | 语言 | `languages`（新字段） | 见 §0.1 修复 |

**「完整」= 上面 13 列 + 下面这些**

| # | 列名 | 来源 |
|---|---|---|
| 14 | 当前公司 / 当前职位 | `currentCompany` / `currentTitle` |
| 15 | 意向职位 / 期望城市 | 分节 `intention`（见 §0.3 修复） |
| 16 | 技能标签 | `skills`（`、` 连接） |
| 17 | 匹配岗位 / 匹配度 | `matches[0].positionTitle` / `.score`（数字列） |
| 18 | 采集来源 / 采集时间 | `sources[0].platform` / `.capturedAt` |
| 19 | 简历编号 | `resumeNo` |
| 20 | 原始简历链接 | `sources[0].resumeUrl`（溯源用；**标注需登录猎聘账号**） |

> 「序号」列都放第一列，方便对着导出的 PDF 逐条核对。

### 1.3 文件名规则

`<岗位>_<日期>_推荐名单.xlsx`，例如：

```
项目经理_2026-10-05_推荐名单.xlsx
C++ 软件工程师（设备控制软件）_2026-10-05_推荐名单.xlsx
全部岗位_2026-10-05_推荐名单.xlsx      ← 没有按岗位筛选时
```

- **岗位**：取当前筛选的岗位；没筛就写「全部岗位」。净化非法字符（见 §0.4），超长截断到 120 字。
- **日期**：`YYYY-MM-DD`（今天）。
- **推荐**：固定写「推荐名单」。

⚠️ HTTP 下发中文文件名必须用 **RFC 5987** 双写：
```
Content-Disposition: attachment; filename="luodi.xlsx"; filename*=UTF-8''%E9%A1%B9%E7%9B%AE%E7%BB%8F%E7%90%86_...
```
只写 `filename=` 的话中文会变乱码（这是最常见的坑，我会在自检里断言 `filename*` 的存在与解码结果）。

### 1.4 文件结构

| Sheet | 内容 |
|---|---|
| **推荐名单** | 第 1 行就是表头（这样**自动筛选**和排序才正常），冻结首行，带列宽 |
| **导出信息** | 岗位 / 筛选条件（人话，如「岗位：项目经理；关键词：MES；最低分：60」）/ 导出时间 / 人数 / 生成工具说明 |

为什么把「导出信息」放第二个 sheet 而不是塞在表格上方：**表格首行必须是表头**，否则你在 Excel 里一按筛选就乱。

### 1.5 接口与入口

```
GET /api/export/candidates.xlsx?q=&positionId=&platform=&status=&minScore=&sort=&preset=brief|full
```

- 服务端生成并以附件下发（浏览器直接下载，不需要前端引入任何库）
- 0 条命中 → **400 + 中文说明**，不下发空文件（空表格容易被误当成"没有人符合条件"以外的意思）
- **入口**：候选人库页头工具栏，在「导出选中 PDF」旁边加 **「导出 Excel」**；旁边一个小下拉/单选选「精简 / 完整」
- 如果当前勾选了人，按钮文案变成「导出选中 Excel」（导出勾选的那些，而不是全部筛选结果）—— 这样两种用法都覆盖

## 二、删除简历设计

### 2.1 一个必须先想清的问题：删了之后**会被重新采回来**

扩展的判重键是 `(平台, 平台内ID)`。你把某人删了，明天又点开他的简历，**扩展会当成新简历再采一次存进来** —— 用户会觉得「删了怎么又回来了」。

所以删除要带一个选项：

```
┌─ 删除这份简历？ ───────────────────────────┐
│ 李先生 · MES资深工程师 · 盐城              │
│ 当前进度：已沟通（面试中）                 │
│ 关联岗位：C++ 软件工程师（设备控制软件）    │
│                                            │
│ ☑ 同时设为「不再采集此人」（推荐）          │
│    勾了之后，即使以后又打开他的简历，       │
│    扩展也不会再存进来。                     │
│                                            │
│         [ 取消 ]      [ 确认删除 ]         │
└────────────────────────────────────────────┘
```

### 2.2 服务端

| 接口 | 作用 |
|---|---|
| `DELETE /api/candidates/:id?forget=1` | 级联删除该候选人 + 他的全部 `sources` + 全部 `matches`；`forget=1` 时把他的 `(platform, platformCandidateId)` 加进「不再采集」名单 |
| `GET /api/ignored` | 列出「不再采集」名单（给人看的：姓名 + 平台 + 时间） |
| `DELETE /api/ignored/:id` | 移出名单（恢复采集） |

**三件必须做的事**：

1. **删前归档**：整条记录（含正文、来源、匹配）写到 `招聘agent-data/_deleted/<时间戳>/<候选人id>.json`。
   和 `_backup/` 一个思路 —— 误删能手工捞回来，而不是彻底没了。
2. **`ingestCapture` 先查名单**：命中就直接返回 `{ ignored: true }`，**不建档、不排队重试**，扩展回执显示「这位你已删除并设为不再采集」。
   ⚠️ 这个判断要放在**创建之前、判重之后**，且不能因为「已存在」而绕过名单。
3. **删完 bump revision**，看板自动刷新（沿用现有机制）。

### 2.3 前端

- **候选人抽屉**：右上角在「导出 PDF」旁加 **「删除」**（次要样式，红色描边），走上面的确认框。
- **候选人库**：勾选框已经为了「导出 PDF」加过了 → 顺手加 **「删除选中」**（同样弹确认框，写明「将删除 N 人」）。批量删除**默认不勾**「不再采集」（批量时误勾代价大，需要用户主动勾）。
- **设置/入口**：在候选人库页头或岗位管理页放一个小的「不再采集名单（N）」链接，点开能看到并移除。N=0 时隐藏。

### 2.4 需要你拍板的点

- **要不要允许删除已到「Offer / 入职」的候选人？** 我建议**允许**（这是你的数据），但确认框里明确写出当前进度，避免误删掉在途流程。
- **「不再采集」名单要不要能一键清空？** 建议单个移除即可，不做一键清空（误操作成本不对称）。
