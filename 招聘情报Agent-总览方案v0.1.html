招聘情报 Agent · 总览方案

无感采集简历 → 云端归类 → JD 匹配 → 每日简报 → 人才 Map，一个闭环。
版本 v0.1 · 待评审 · 2026-09-30 · 面向：招聘 HR / 招聘负责人
一句话结论
不做「写爬虫去扒简历」。做一条「无感沉淀 → 云端归类 → 大模型匹配 → 每日推谁 → 人才地图」的流水线。
采集端用浏览器扩展（只读你已登录、页面上肉眼可见的内容），云端用托管数据库 + 大模型，展示端一个 Web 看板，最后打包成可调用的 Skill 并发布上线。
采集通道分两级：被动采集（默认，零操作、低风险） + 主动 MCP（可选，批量搜索用）。

1 · 你的需求，拆成 6 个能力

无感采集在线简历 + 离线简历文件
云端归档按岗位 / 候选人结构化
智能归类岗位归类 + 同一人合并
检索问答关键词 + 自然语言
提取待办进度节点 + 跟进提醒
简报地图每日「推谁」+ 人才 Map
  1. 无感采集：你在 BOSS / 猎聘上点开过的每一份简历（在线），以及你下载的离线简历（PDF / Word / 图片），自动进库，不用手动复制粘贴。
  2. 云端归档：所有候选人存到云端，按「岗位」分门别类，网页端随时看。
  3. 智能分类与关联：自动把候选人归到对应岗位族；同一个人在多平台 / 在线+离线出现时自动合并；技能标签归一（「大模型 / LLM / AIGC」算一类）。
  4. 检索与问答：既有关键词检索，也能自然语言问（「帮我找有半导体量测经验、5 年以上的候选人」）。
  5. 信息提取与待办整理：从简历和沟通记录里提取关键信息（期望薪资、到岗时间、当前状态），生成待跟进清单。
  6. 阶段总结 + 行动建议：按 JD 匹配度，每天出「哪些岗位该推谁」的清单；人才 Map 看板看整体盘面。

2 · 关键调研：BOSS / 猎聘到底有没有 API 和 MCP

这决定了整个采集层怎么设计，先说结论：两家都没有面向第三方的公开简历 API，官方「开放平台」也不对路。所以 MVP 不能依赖官方接口。

平台官方 API「开放平台」真相社区 MCP 现状工程上可用手段风险
BOSS 直聘
zhipin.com		 无公开简历 API open.zhipin.com 是 BOSSHI 小程序身份体系（bz.login / code2session），与招聘数据无关，不能用来拉职位/简历 存在多个：Snseam/boss-zhipin-mcp（招聘端，候选人搜索+简历截图+AI 打分）、mucsbr/mcp-bosszp；均走 Playwright + 已登录 Chrome（CDP） 登录态 wapi JSON 接口 + Playwright DOM 兜底；图片型简历走截图 + 多模态识别 高 风控严格，高频 / 批量打招呼会封号
猎聘
liepin.com		 企业版接口需商务对接 api.liepin.com / open.liepin.com 存在，但面向企业 ATS 集成，需签约，非自助注册 暂无成熟公开 MCP 社区逆向搜索接口 api-c.liepin.com/api/com.liepin.searchfront4c.pc-search-job（POST + JSON，需 XSRF-TOKEN） 中高 有反爬与 Token 校验

一个重要旁证：这条路已经被商用验证过

市面上已有同类产品在跑，说明「浏览器扩展读已授权页面」的路线技术上成立、也不是没人做过：

  • KingStar 招聘助手：在 BOSS「沟通列表 / 推荐牛人」页一键整理本页候选人，按岗位要求打分，导出 HTML / CSV —— 和你的需求几乎重合。
  • 奇客大师简历采集插件：采集猎聘、智联、前程无忧、LinkedIn 简历，对接自家 ATS（基于 Odoo）。
  • Boss直聘 AI 简历助手(for HR)：自动遍历推荐牛人 / 搜索牛人 / 沟通页简历，AI 打分。

共同点：都由用户本人登录、只读页面可见内容、不绕过风控——这就是我们为 MVP 选定的边界。

3 · 总体架构（五层）

采集层
Chrome/Edge MV3 扩展「简历捕手」 —— 被动：注入 zhipin/liepin，监听你打开的简历页自动抓取；离线：拖拽上传 PDF/Word/图片。
（可选）MCP Server —— Playwright + CDP 接你已登录的 Chrome，批量搜索「找人才」并翻页。
存储层
云数据库（Postgres）：候选人 / 岗位 / 匹配 / 进度 / 待办 / 简报。对象存储：原始简历文件与页面快照。认证 + 行级权限 RLS：各账号数据互相隔离。
智能层
大模型流水线：简历结构化 → JD 结构化 → 匹配打分（可解释）→ 岗位归类 → 实体归一 → 每日简报 → 智能问答（RAG）。
展示层
Web 看板：候选人库（按岗位分组）· 岗位看板（漏斗）· 每日简报 · 人才 Map · 问答框 · 待办中心。
发布层
一键上线：站点部署 + 云端后端，生成可分享链接；打包 Skill 供对话内直接调用（查库 / 出简报）。

数据流（无感采集 → 看板）

你点开一份简历 │ ▼ [扩展 content script] 监听 SPA 路由 + DOM 变化 → 提取字段 │ · 文本型简历：直接读 DOM │ · 图片型简历（BOSS canvas 渲染）：整屏截图 → 多模态模型解析 ▼ [本地 IndexedDB 缓冲] → 去重（平台ID + 姓名/电话 hash） │ · 静默：仅在空闲时批量上传，断网可恢复 ▼ [云端 API + 队列] → 大模型结构化 → 落库（对象存储留存原始文件） │ ▼ [匹配引擎] 简历 × 你的 JD → 0–100 分 + 命中/缺失理由 │ ▼ [Web 看板] 候选人库 / 岗位漏斗 / 每日简报 / 人才 Map / 问答

4 · 采集层设计（「无感」是重点）

4.1 在线简历 —— 被动、零操作

  • 触发方式：监听 SPA 路由与 DOM 变化，你打开某人简历（列表点开 / 详情页 / 沟通页）即自动抓取，不改变你的操作习惯。
  • 提取字段：姓名 / 性别 / 年龄 / 城市 / 学历 / 院校 / 专业 / 工作年限 / 现任公司与职位 / 期望薪资 / 求职意向 / 技能标签 / 工作经历 / 项目经历 / 自评 / 平台候选人 ID / 简历来源链接。
  • 图片型简历：BOSS 部分简历是 canvas 渲染、DOM 里没有文本 → 整屏截图，交给多模态模型（视觉 LLM）解析成结构。
  • 去重：平台候选人 ID 为主键；跨平台用「姓名 + 手机/邮箱」哈希兜底。
  • 静默同步：本地 IndexedDB 先缓冲 → 后台 service worker 空闲时批量上传；断网 / 关页不丢数据。
  • 风控友好：只在你主动浏览时触发，扩展不自己发起并发请求 → 账号风险降到最低。
  • 可控开关：悬浮指示器显隐、暂停采集、岗位白名单。

4.2 离线简历 —— 拖拽即入库

  • 支持 PDF / DOC / DOCX / JPG / PNG，拖拽或选文件夹批量导入。
  • 自动解析入库，并与「在线简历」做同一人合并（走 4.1 的去重逻辑）。

4.3 主动采集（可选，P3）

  • MCP Server：Playwright 通过 CDP 连接你已登录的 Chrome，按关键词在「找人才 / 推荐牛人」批量搜索、翻页抓取。
  • 与被动通道解耦，默认关闭，需手动触发；内置限速 + 熔断（遇到风控立即停止）。

6 · 智能层（大模型流水线）

  1. 简历结构化：原文（或截图）→ 标准 JSON 档案。
  2. JD 结构化：把你粘贴的 JD → 硬性条件 / 加分项 / 技能清单。
  3. 匹配打分：先向量召回，再 LLM 精排，输出 0–100 分 + 命中点 / 缺失点（可解释、可核对）。
  4. 岗位自动归类：把候选人自动归到你的岗位族。
  5. 实体归一：同一人多平台合并；技能同义词归一（大模型/LLM/AIGC → 同一标签）。
  6. 每日简报：今日已看 N 人 → 各岗位分布 → 每岗位 Top 推荐 + 推荐理由 → 待跟进清单。
  7. 智能问答：在你的候选人库上做 RAG，自然语言问、自然语言答。

8 · 交付形态（你要能「调用」）

  • Web 应用（发布链接）—— 主入口，看板与简报。
  • 浏览器扩展 —— 采集端，你日常浏览时无感运行。
  • Skill —— 在对话里直接调用：查库、生成简报、问候选人。
  • （可选）MCP Server —— 让 Agent 主动批量采集。

9 · 合规与风控红线（务必先对齐）

  • 简历属于个人信息，受《个人信息保护法》约束。仅限本人招聘目的、授权范围内使用，禁止二次传播 / 贩卖。
  • 只采集你已登录、页面已展示的内容，不绕过登录 / 验证码 / 风控。
  • 平台协议：不做多账号、无人值守高频抓取、批量打招呼 / 自动投递。
  • 数据隔离：行级权限，每账号仅见自己数据；支持导出与删除。
  • 保留审计日志：谁在何时采了什么，来源 URL 可追溯。

10 · 分期路线图

P0 MVP
先跑通闭环：扩展采集 BOSS 在线简历 + 离线简历上传 + 云端库 + 候选人看板（按岗位分组）+ 关键词检索。最小可用
P1
智能化：LLM 结构化 + JD 匹配打分 + 每日简报「推谁」。
P2
丰富化：智能问答 + 人才 Map 看板 + 猎聘通道 + 图片简历多模态 OCR。
P3

11 · 需要你拍板的 6 件事

1
采集范围：先只做 BOSS，还是 BOSS + 猎聘一起上？
猎聘接口需额外适配 Token，成本更高。
2
主动 or 被动：接受「被动采集 + 手动上传」的 MVP，还是一开始就要 MCP 主动批量搜索？
主动采集更快出量，但账号风险更高、维护更重。
3
岗位族：你负责的岗位大概几个、是否固定？
影响「岗位自动归类」怎么设计——固定少量岗位可规则化，多且变动大则靠模型聚类。
4
使用范围：只有你自己用，还是团队一起用？
影响认证、权限、数据隔离的复杂度。
5
大模型：用平台自带的免密钥调用，还是接你自己的 API Key？
影响成本与数据出境口径。
6
合规口径：是否需要审计日志、离职数据清理机制？
大公司通常对个人信息留存有硬要求，建议默认开启。
